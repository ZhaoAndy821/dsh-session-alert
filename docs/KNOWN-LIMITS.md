# 已知限制 / 待办细节（2026-09-27）

这份说明只记录**已确认存在、但当前判定为细枝末节**的问题：它们不影响提醒功能、不涉及凭据或隐私，因此没有立刻动代码。
每条都写了触发条件、实际影响和修法，方便日后要处理时直接照着做。

## 1. 测试残留的临时目录（已修）

- **现象**：测试在 `%TEMP%` 下建 `dsh-alert-test-*` 等目录；正常运行会自己删掉，但**中止路径**（自守护触发、意外抛错）会跳过清理并留下目录。实测同一台机器上累积了 25 个（约 35 KB）。
- **处理**：已清理存量，并在 `test/bridge.mjs` / `test/singleton.mjs` / `test/supervise.mjs` 里注册 `process.on('exit')` 清理钩子；实测"全量跑完"与"强制中止"两种情况下残留都为 0。
- **剩余**：无。

## 2. `engines` 与实测引擎版本

- **现象**：`package.json` 声明 `node >= 20`，而 `test/bridge.mjs` 里那条"V8 回显片段"的自守护规则是在 Node 24 上实测的。
- **影响**：换到别的 Node 版本时，若该规则不成立，守卫会**直接中止并打印原因**（而不是让断言空转通过）——这是刻意设计，不是缺陷。
- **修法**：要么在 CI 里固定 Node 版本，要么把这条断言改成"只在 Node 24 上启用、其他版本跳过并提示"。

## 3. EADDRINUSE 竞争窗口（R4 残留）

- **现象**：两个 bridge 同时启动时，落败方会重探端口最多 3×400ms；如果**在位的那个进程**正好卡住事件循环超过约 3.2 秒，落败方会认为"那个端口不是本服务"并换到下一个端口，于是短暂出现两个都在服务的实例。
- **影响**：只是多一个监听者；没有任何数据面损害（通知会重复投递一次）。pre-bind 探活本身仍是单发。
- **修法**：把"重探"改成带退避的多轮（例如 6×500ms），或在绑定失败后先尝试与在位实例握手（例如 `/health` 里带进程启动时间）再决定是否换端口。

## 4. `probeHeld` 把"外来服务/挂死套接字"也算进重探窗口

- **现象**：某个端口被**非本服务**的 HTTP 程序占用（响应不是本服务的 JSON），或对端只连不答时，探活要等满整个重探窗口才判定并继续换端口。
- **影响**：实测多等 0.46s（非 JSON 响应）/ 2.4s（挂死套接字），只在启动路径上发生一次。
- **修法**：非 2xx 或非 JSON 响应可以直接判定"不是本服务"并立刻换端口。

## 5. `checkMs = deps.checkMs || CHECK_MS`

- **现象**：`desktop/supervise.mjs` 里这行与先前修掉的 `retryMs` 同构——注入 `0` 会被当成"未注入"而回落到默认值。
- **影响**：只是测试注入的语义不精确，产品路径始终用默认值。
- **修法**：改成 `deps.checkMs ?? CHECK_MS`。

## 6. 宿主半边与 pid 判活

- `host/index.js` 的 `bridgeScript()` **不认** `DSH_DESKTOP_ALERT_DIR`：宿主只会从自己的布局里找 `bridge.mjs`。把运行目录换到别处时，宿主拉起的仍是它自己那份（功能正常，只是与手工安装的那份不是同一个文件）。
- `desktop/cli.mjs start()` 的 spawn **没有 `'error'` 监听**（R8）：可执行文件缺失时错误会以未处理事件的形式冒泡，而不是打出可读提示。
- `anotherSupervisorRunning` / `supervisorAlive` **只判存活**（R11）：pid 被系统复用时，一个不相关的进程会被误认成"守护还在跑"。
- **修法**：宿主的 `bridgeScript()` 先读环境变量；start 的 spawn 挂 `error` 监听；判活时比对进程启动时间（或写入一个含启动时间的 lock 文件）。

## 7. devDependency 未锁版本

- `playwright-core` 写的是 `^1.63.0`，仓库里也没有 lockfile，`npm install` 可能装到不同版本。
- **影响**：只影响 `npm run check:browser`（真页面校验）的可复现性。
- **修法**：提交 `package-lock.json`，或把它钉成精确版本。

---

以上都不影响桌面提醒的正常工作。若其中某条在真实使用中造成了麻烦，按"修法"一列处理即可。
